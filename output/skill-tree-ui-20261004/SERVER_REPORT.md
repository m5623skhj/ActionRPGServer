# 스킬 트리 서버 구현

현재 상태: 서버·클라이언트 소스, 공용 계약과 아이콘 통합 및 정적 검토 완료. 빌드·테스트·게임 실행은 하지 않았다.

## 확정 정책

* 접속 시 캐릭터 레벨 1, SP 0. 레벨업당 200 SP.
* 이번에는 경험치 획득/자동 레벨업 조건과 영구 저장을 구현하지 않는다.
* 레벨/SP/습득 정보는 Town의 플레이어별 메모리에 둔다. 마을/던전 전환 중 유지하고 접속 종료 시 제거한다.
* 앞차기는 요구 캐릭터 레벨 1, 매 단계 20 SP, 공격력 25에서 단계마다 5 증가한다.
* 모든 스킬의 단계별 요구 캐릭터 레벨은 최초 요구 레벨 + 2 × (스킬 레벨 - 1)이다.
* 최대 스킬 레벨은 선택적이다. 앞차기는 기획상 상한 미지정(null)이다. 직렬화와 계산의 정수 범위 검증은 적용한다.

## 소스 구성

* Shared/CharacterProgression.h: 레벨, 남은 SP, 습득 스킬 레벨과 데이터 기반 SP 지급 정책.
* Shared/SkillTreeCatalog.h: 스킬 소유자/요구 레벨/SP/선행 조건/최대 레벨 검증, 습득과 단계별 공격력 계산.
* TownServer/Data/CharacterProgression.json: 초기 정책과 레벨업 SP.
* TownServer/Data/PlayerSkills.json, SkillTrees.json: 실행 스킬과 습득·표시 데이터.
* GameRoomServer/Data/SkillTrees.json: 같은 스킬 트리 계약. 기존 PlayerSkills.json의 실행 계약 v1은 유지한다.
* TownInstance::AdvancePlayerLevel: 향후 서버 레벨업 로직 연결 API. 같은 레벨/낮은 레벨 요청이나 SP 오버플로는 거절한다. 클라이언트가 레벨을 올리는 패킷은 없다.

## 습득 흐름

1. Town 접속 직후와 SkillStateRequest에 SkillStateResponse를 보낸다.
2. 응답 JSON은 characterId, progression, skillTrees, playerSkills, result를 포함한다.
3. LearnSkillRequest는 skillId와 expectedSkillLevel만 받는다. 캐릭터와 현재 레벨/SP는 서버 소유 상태에서 읽는다.
4. Town strand에서 캐릭터, 요구 레벨, 모든 선행 스킬 최소 단계, SP와 최대 레벨을 검사한다.
5. 성공 시 SP 차감과 스킬 단계 증가를 같이 반영하고 결과 상태를 보낸다.
6. 동일 예상 단계의 요청을 재전송하면 StaleSkillLevel로 거절하므로 중복 구매로 해석하지 않는다.

선행 조건의 누락 참조, 자기 참조, 다른 캐릭터 참조, 중복, 순환과 도달 불가능한 선행 단계는 데이터 로드에서 거절한다. 모든 실제 스킬에는 트리 노드가 있어야 한다.

## 던전 연결

* 서버 간 인증된 제어 채널의 ConfirmJoin에 성장 상태를 넣는다. 클라이언트가 습득 목록을 선언해 권한을 얻지 않는다.
* 접속 중 습득/레벨 변경은 UpdatePlayerProgress로 전달하고 GameRoom strand에서 상태 사본을 검증·반영한다.
* SubmitSkill은 서버 소유 습득 단계가 0이면 거절한다. 커맨드와 단축키는 모두 같은 서버 판정을 받는다.
* 공격력은 실행 데이터의 기본 공격력과 트리의 damagePerLevel로 계산한다. 시전 시 스킬 단계를 고정해 진행 중인 공격이 강화 요청 때문에 바뀌지 않는다.
* 기존 JSON 전투 상태에 level, skillPoints, skillLevels, skillCooldowns를 추가한다. 기존 실시간 바이너리 포맷은 변경하지 않는다.
* 공용 TCP 패킷 ID는 기존 순서를 보존하고 YAML 끝에 3개 패킷을 추가했다. 기존 생성기로 서버/클라이언트 선언을 생성했다.

Town, RoomControl, RoomManager와 GameRoom은 각 소유 strand에서만 가변 상태를 처리한다. 네트워크 사이에는 값 사본을 전달한다.

## 아이콘 반영

* 제작 결과를 확인하고 클라이언트 소스 Assets/Images/UI/Skills/character1_front_kick.png 및 Assets/Images/UI/system_menu_skills.png에 복사했다.
* 실제 PNG는 1254×1254 RGBA이며 정해진 UI 표시 크기로 축소한다. 권장 원본 128×128과 동일 여백·완전 무잔여 알파 기준의 차이는 graphics/GRAPHICS_REPORT.md에 기록했다.
* 실행 중 프로그램이나 빌드 출력 폴더는 수정하지 않았다.

## 클라이언트 연결

* 메뉴의 스킬 항목에서 해당 캐릭터의 전체 트리, 습득 조건, 설명, 단계별 공격력, 쿨타임과 SP를 표시한다.
* 습득한 스킬만 A/S/D/F/G/H로 드래그 등록할 수 있다. 교체, 중복 제거, 오른쪽 클릭 해제와 슬롯 밖 취소를 처리한다.
* 슬롯 설정은 LOCALAPPDATA/ActionRPGClient의 캐릭터별 파일에 저장한다. 레벨/SP/습득 상태는 파일에 저장하지 않는다. 프로세스별 임시 파일과 자동 정리로 두 클라이언트의 임시 파일 충돌을 피한다.
* 커맨드와 단축키는 같은 사용 판정을 거치며 사용할 수 없는 입력을 보관하지 않는다. 기존 일반 공격/점프 버퍼를 제거하지 않는다.
* 던전 서버의 승인 응답 이후 쿨타임 표시를 시작하고 JSON 상태로 보정한다. 실시간 위치 스냅샷의 기본값이나 이전 승인 전 상태가 쿨타임을 덮어쓰지 않도록 순서를 확인한다.
* Town의 스킬 상태 응답이 성장 권위를 갖는다. Room JSON은 검증 후 쿨타임에만 반영하여 이전 전투 상태가 최신 습득을 되돌리지 않게 한다.
* 기본 슬롯 64×80/아이콘 56×56, 작은 창 아이콘 48×48, 상세 아이콘 96×96이다. 회색 효과와 남은 x.x초/정수 m 표시는 런타임에서 그린다.
* UI 구성, 입력, 렌더링 리소스 갱신은 게임 스레드에서 수행한다. 네트워크 이벤트를 게임 스레드에서 적용한다.
* 자세한 클라이언트 변경 내역은 ../skill-ui-20261004/CLIENT_UI_HANDOFF.md에 기록한다.

## 정적 확인과 한계

* Town/GameRoom의 PlayerSkills.json과 SkillTrees.json이 바이트 기준 동일한지 확인했다.
* 실제 데이터 JSON을 읽어 실행 스킬과 트리 노드 ID 집합이 일치하는지 확인했다.
* 생성 코드, 선언/호출 경로, 범위 검증 및 변경 diff를 검토했다.
* 서버/클라이언트 공용 헤더와 패킷 선언의 바이트 일치, 프로토콜 소스의 include 경로 이외 일치, 프로젝트 XML과 UI JSON을 확인했다.
* 새 스킬 창을 여는 클릭이 습득/드래그 처리로 중복 전달되지 않도록 소비 여부를 반영했다.
* 기존 마을 가시성 테스트의 fixture에 새 필수 데이터 파일 복사를 추가했으며 테스트는 실행하지 않았다.
* 현재 캐릭터는 자동 레벨업 기능이 없고 SP 0이므로 처음에는 앞차기도 잠긴다. 향후 서버 레벨업 로직이 API를 호출해야 플레이 중 SP를 획득한다.
* 클라이언트/서버 소스를 함께 빌드해야 새 패킷을 사용할 수 있다. 현재 EXE를 빌드하거나 교체하지 않았다.
